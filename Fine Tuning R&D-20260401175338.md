## Introduction
This document presents comprehensive research and development findings on fine-tuning large language models, specifically focusing on OpenAI OSS models using Unsloth framework. The documentation covers critical aspects of dataset formatting, model training methodologies, inference strategies, deployment procedures, and advanced techniques like continued pretraining.
The research addresses key challenges in fine-tuning quantized models, particularly the complexities of working with MXFP4 quantization, and provides practical solutions for achieving optimal performance while maintaining computational efficiency. Special attention is given to multilingual capabilities and domain adaptation through continued pretraining techniques.

### 4.2 Technical Analysis: Why Merged Models Fail
#### 4.2.1 Model Architecture Overview
**MXFP4 Structure**:
*   OpenAI OSS models use Microscaling FP4 quantization
*   32-element blocks sharing single 8-bit scaling factors
*   Each element uses 4-bit E2M1 format (1 sign, 2 exponent, 1 mantissa bit)
*   Storage: `tensor.blocks` (packed 4-bit values) + `tensor.scales` (block scaling factors)
**MLP Architecture**:
*   Mixture-of-Experts (MoE) with gated SwiGLU activation
*   **gpt-oss-20b**: 32 experts per layer, top-4 routing
*   **gpt-oss-120b**: 128 experts per layer, top-4 routing
*   MoE weights comprise 90% of total parameters (~19B of 21B)
*   Stored as `nn.Parameter` objects in MXFP4 format rather than standard `nn.Linear` layers
#### 4.2.2 Root Cause: Precision Conversion Chain and Context Mismatch
**Complex Precision Conversion Chain**:
1. **Training Phase**: MXFP4 → BF16 upcast (introduces specific artifacts)
2. **LoRA Training**: BF16 adapters learn on upcasted weights with artifacts
3. **Merging Phase**: MXFP4 → BF16 → merge with LoRA → target precision
**Why MXFP4 Is Harder to Merge**:
*   **Block-Based Scaling Incompatibility**: Unlike standard quantization schemes that use per-tensor or per-channel scaling, MXFP4's 32-element blocks with shared scaling factors are optimized for specific weight distributions. LoRA adjustments span multiple blocks and change weight distributions, breaking the original optimization.
*   **Cross-Block Dependencies**: LoRA adjustments don't respect MXFP4's fixed block boundaries. When merging, a single LoRA weight change affects the optimal scaling factor for an entire 32-element block, requiring re-optimization of all values in that block.
*   **Scale Factor Propagation**: Changing weights within a block necessitates recomputing the shared 8-bit scaling factor, which then affects the quantization of all other elements in the block, amplifying precision errors beyond the original LoRA adjustment locations.
**Comparison**: Standard INT4/NF4 quantization allows simple dequantize→merge→requantize operations. MXFP4 requires complex block-wise re-optimization that destroys the original quantization structure and mathematical relationships the model was trained on.

## 6\. Continued Pretraining (CPT)
### 6.1 Overview
Continued Pretraining is a specialized method for teaching models new vocabularies or domain-specific knowledge where the original training data was limited or absent.
### 6.2 Methodology
*   **Training Data**: Plain text to enable new embedding understanding and generation
*   **Layer Focus**: Targets specific layers responsible for embedding understanding and generation
*   **Selective Training**: Doesn't train all model layers, focusing on critical components
*   **Instruction Tuning :** After this we can fine tune with instruction tuning or chat template.
### 6.3 Key Components: embed\_tokens and lm\_head
#### 6.3.1 embed\_tokens: The "Dictionary" Layer
**Function**: Converts words/tokens into mathematical vectors for model comprehension.
**Process**:
*   **Input**: Raw token IDs (numerical word representations)
*   **Process**: Lookup corresponding embedding vector for each token
*   **Output**: Dense vectors capturing semantic meaning
**Example**:

```scss
Token "গণিত" (ID: 45231) → [0.2, -0.1, 0.8, 0.3, -0.5, ...] (4096 dimensions)
Token "math" (ID: 12456) → [0.1, -0.2, 0.7, 0.4, -0.3, ...] (4096 dimensions)
```

**Vector Representation**:
*   **Semantic Similarity**: Similar concepts have similar vectors
*   **Relationships**: Mathematical relationships encoded in vector space
*   **Context**: How words typically appear together
**Before CPT (Base Model)**:
*   **English tokens**: Rich, well-trained vectors with extensive context
*   **Bengali tokens**: Sparse, poorly trained vectors (limited Bengali exposure during original pretraining)
*   **Result**: "গণিত" might resemble random noise rather than "math"
**After CPT**:
*   **Bengali tokens**: Rich vectors capturing mathematical meaning
*   **Cross-lingual alignment**: "গণিত" and "math" become semantically close
*   **Domain knowledge**: Mathematical Bengali terms cluster together appropriately
#### 6.3.2 lm\_head: The "Prediction" Layer
**Function**: Final prediction layer that converts processed information from transformer layers into vocabulary probabilities. Essentially the "reverse" of embed\_tokens.
**Process**:
*   **Input**: High-dimensional hidden states from last transformer layer
*   **Process**: Linear transformation projecting hidden states to vocabulary size
*   **Output**: Probability distribution over all possible next tokens
**Example**:

```perl
Hidden state: [0.3, 0.7, -0.2, 0.1, ...] (4096 dimensions)
                     ↓ lm_head projection
Probabilities: {
  "গণিত": 0.001,    # Low probability before CPT
  "math": 0.023,    # Higher because model knows English
  "the": 0.089,     # Common English word
  ...
}
```

**Before CPT**:
*   **English bias**: High probabilities for English mathematical terms
*   **Bengali penalty**: Very low probabilities for Bengali tokens, even when contextually appropriate
*   **Poor predictions**: Model struggles to generate coherent Bengali
**After CPT**:
*   **Contextual awareness**: When processing Bengali input, assigns higher probabilities to Bengali continuations
*   **Domain adaptation**: Learns that after "সমীকরণ" (equation), mathematical symbols or Bengali terms are more likely
*   **Balanced predictions**: Can switch between languages based on context
### 6.4 Critical Relationship Between embed\_tokens and lm\_head
#### 6.4.1 Mirror Architecture
*   **embed\_tokens**: vocabulary\_size → hidden\_size (compress words into meaning)
*   **lm\_head**: hidden\_size → vocabulary\_size (expand meaning into words)
#### 6.4.2 Vocabulary Consistency
Both layers must understand the same vocabulary space. If embed\_tokens learns that "গণিত" represents mathematical concepts, lm\_head must learn to predict "গণিত" when mathematical concepts are expected.
#### 6.4.3 Information Flow

```elixir
"একটি সমীকরণ" → embed_tokens → transformer layers → lm_head → "সমাধান করতে"
     ↑                                                        ↓
   Input tokens                                         Predicted next token
```

### 6.5 Update Scenarios and Outcomes
#### 6.5.1 Scenario 1: Only embed\_tokens Updated
*   **Problem**: Model can understand Bengali input better, but can't generate Bengali output
*   **Result**: Understands "গণিত সমস্যা" but responds in English
*   **Why**: lm\_head still biased toward English predictions
#### 6.5.2 Scenario 2: Only lm\_head Updated
*   **Problem**: Model can generate Bengali tokens, but doesn't understand Bengali input well
*   **Result**: Generates Bengali-looking gibberish
*   **Why**: Poor input understanding leads to meaningless outputs
#### 6.5.3 Scenario 3: Both Updated (Correct Approach)
*   **Benefit**: Full input-output cycle in Bengali
*   **Result**: Understands Bengali mathematical questions AND responds in coherent Bengali
*   **Why**: Complete language adaptation at both ends
### 6.6 Learning Process Details
#### 6.6.1 embed\_tokens Learning Process
*   **Frequency exposure**: Bengali tokens appear more often in training data
*   **Context learning**: "গণিত" appears near mathematical symbols and concepts
*   **Vector refinement**: The embedding vector for "গণিত" gets adjusted to be similar to mathematical concept vectors
*   **Relationship mapping**: Learn that "সমীকরণ" (equation) relates to "সমাধান" (solution)
#### 6.6.2 lm\_head Learning Process
*   **Pattern recognition**: After Bengali mathematical terms, Bengali continuations are correct
*   **Probability adjustment**: Increase likelihood of Bengali tokens in Bengali contexts
*   **Domain adaptation**: Mathematical contexts should predict mathematical vocabulary
*   **Language consistency**: Don't switch languages mid-sentence unless appropriate
### 6.7 Learning Rate Considerations
#### 6.7.1 Why embedding\_learning\_rate is Lower
*   **Catastrophic forgetting risk**: These layers control fundamental language understanding
*   **Stability requirement**: Don't want to destroy existing English capabilities
*   **Gradual adaptation**: Slowly shift toward better Bengali representation
*   **Preservation**: Keep existing useful cross-lingual relationships
#### 6.7.2 Learning Rate Impact
*   **Same learning rate**: Risk destroying English mathematical understanding
*   **Lower embedding rate**: Gradually adapt while preserving existing knowledge
*   **No embedding updates**: Bengali remains poorly represented
### 6.8 Real-World Impact Demonstration
#### 6.8.1 Before CPT
**Input**: "এই সমীকরণটি সমাধান করুন: x + 5 = 10" **Model Processing**: "Some foreign text... let me respond in English" **Output**: "To solve this equation: x + 5 = 10, subtract 5 from both sides..."
#### 6.8.2 After CPT
**Input**: "এই সমীকরণটি সমাধান করুন: x + 5 = 10" **Model Processing**: "This is asking to solve an equation in Bengali" **Output**: "এই সমীকরণটি সমাধান করতে: x + 5 = 10, উভয় পক্ষ থেকে 5 বিয়োগ করি..."
The enhancement occurs simultaneously in both understanding (embed\_tokens) and generation (lm\_head) capabilities, creating a truly bilingual mathematical model.
